## Divergences

### #2
- decisions.md says: "The Origin gate belongs to WSX handshake processing; raw applications own their handshake policy after the server state gate."
- the implementation says the same thing: `wsx.py:271` `_origin_refusal` is reached only from the WSX gate (`wsx.py:249`), and the state gate stands above the demux at `server.py:482-484` `if self.state != RUNNING:` / `await WebSocket(scope, receive, send).refuse(1013, "server restarting")` / `return`, before `server.py:485` `app, target = self.demux(scope)`. Both modes are refused by the same refusal: `tests/core/test_websocket_raw_seam.py::test_a_server_that_is_not_running_never_reaches_it` asserts `[{"type": "websocket.close", "code": 1013, "reason": "server restarting"}]` and `assert app.seen == []`, and `::test_a_server_that_is_not_running_refuses_it_the_same_way` asserts the identical list for the non-raw application.
- the docstring says the same thing. `wsx.py:59-63` places the Origin inside the WSX gate and states "The state of the server is judged higher up, in ``on_websocket``, above the demux and for every websocket alike"; `websocket.py:162-163` `refuse` "Turn the handshake away without accepting it."
- the handoff of 2026-09-07 (`temp/issue_genropy_asgi_websocket_2026-09-07.md`, lines 23-24) says: "Origin (the only refusal WITHOUT accept), then accept and close with a readable code — 1013 while the server is not RUNNING". The state refusal is therefore described there as following the accept and the Origin as the only refusal without an accept; in the code at `9ebfa56` the state refusal too is without an accept and stands above the demux.
- the transcript `60d6d5d6-c863-414c-8eec-a8deb8c89af4.jsonl` of 2026-09-06 says, uuid `a35dc9af-ea91-4246-a0d2-5e5b28380278` (assistant): "lo stato del server sale in cima a `on_websocket`, sopra il demux, per ogni websocket. Il controllo dentro `_open_gate` cade. Il rifiuto cambia forma come previsto: handshake respinto prima dell'accept". The transcript `22ffda80-8621-47db-8a2b-57eff4410c26.jsonl` of 2026-09-08, uuid `d4fc8323-04db-4a9e-a510-5a1fbfe6d077` (assistant), records the same correction on another document: "«Il server non RUNNING rifiuta prima dell'accept, per raw e WSX»: corretto, `server.py:392` chiama `refuse` prima del demux. Il testo precedente («chiude 1013 dopo l'accept») era stale."

### #3
- decisions.md says: "an application cannot answer a WebSocket. The only WebSocket door is the server's, and at the base it accepts the connection and closes it politely; no composition hands a socket to an application".
- the implementation at `server.py:486-489` does the opposite: `raw_seam = getattr(app, "serve_websocket", None)` / `if raw_seam is not None:` / `await raw_seam(target, receive, send)` / `return`. The composition that hands the socket over is the presence of the method on the application, and `tests/core/test_websocket_raw_seam.py::test_it_accepts_and_answers_in_its_own_protocol` proves an application answering a socket in its own protocol. `on_websocket` contains no accept-and-close at the base: the non-raw branch is `server.py:490` `await WsxConnection(self, scope, receive, send).serve()`.
- the docstring says the opposite at commit `9ebfa56`: `server.py:473-476` "The exception is an application that wants the socket ITSELF … if it defines ``serve_websocket`` it is handed the raw scope, receive and send".
- the handoffs of 2026-09-06 confirm the friction as the state of that day: "Il websocket oggi: `BaseServer.on_websocket` (`server.py`) accetta e chiude 1000."
- no transcript names this friction in its own words.
- `decisions.md` itself carries, at its head, the follow-up of 2026-09-08 declaring the friction superseded. Both entries remain in the file.
